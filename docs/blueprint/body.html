1The Project in 60 Seconds

The problem. AI agents can now read the logs and metrics of a broken system and suggest a fix. But a confident AI can suggest a harmful fix, such as switching off a healthy server. Letting it act alone is risky. Asking a human every time defeats the point.

The idea. Treat the AI as an untrusted planner: it may only suggest. Every suggestion must pass a safety checker (the verifier) before anything happens. The checker has three layers:

  1. a fixed rule list, the envelope, which needs no AI;
  2. an AI reviewer, the LLM judge;
  3. a trained machine-learning model that estimates how likely the action is to cause harm.

A threshold called τ (tau) decides how cautious the checker is.

The proof. The project replays 41 saved incidents thousands of times and measures how many harmful actions get through. With the learned layer, harmful actions reached execution in about 1% of runs, down from about 33% with no checker. A web console shows all of this live.

2How the Folders Fit Together

Table 1. The top-level folders.
FolderIn one line
src/sentinel/The backend, written in Python: agent, safety checker, executor, loop, database, scoring and web server.
frontend/The web console, written in React and TypeScript: the screens you click through in the demo.
config/Settings in YAML: the allow-list, thresholds, labeling rules and monitoring setup.
fixtures/incidents/Test data: 41 saved incidents, each with its answer key.
scripts/Runnable programs: demos, training, the full experiment, dataset tools, document builders.
tests/Automatic checks (about 620) that keep everything working.
docs/Documents: the architecture report, the frontend guide, this blueprint.
notebooks/A Jupyter notebook for exploring the results.
not in git: runs/, data/, .venv/Generated or downloaded: the run database, trained models, figures and screenshots (runs/); the 13 GB raw dataset (data/); the Python environment (.venv/). Commands recreate them.

3Words You Will See

Table 2. Glossary.
WordMeaning
IncidentA broken-system situation to fix, stored as a JSON file.
TelemetryThe evidence about an incident: logs, metrics, traces, alerts and the service map (topology).
AgentThe part that reads the incident and suggests one action. Untrusted.
Proposed actionWhat the agent wants to do, e.g. rollback_deployment on checkout-service.
VerifierThe safety checker that rules on each proposed action.
EnvelopeLayer 1 of the verifier: a fixed allow-list of action types and rules. No AI.
LLM judgeLayer 2a: an AI model asked whether the action is safe. Needs an API key.
Learned verifierLayer 2b: a trained model that estimates the chance an action is destructive.
VerdictThe ruling: allow (may run), block (stopped), or revise (try again).
τ (tau)The risk threshold. An action runs only if its risk is below τ. Lower τ means more cautious.
ExecutorThe only part allowed to apply an action, and only after an allow.
Dry runPlan the action but don't apply it.
Orchestrator / loopRuns propose → verify → act again and again until the incident is fixed.
Oracle / answer keyThe stored truth about which actions fix an incident and which are harmful. Used only for scoring.
LabelThe answer key's verdict on one action: correct, ineffective, destructive or out_of_envelope.
ProvenanceWhere a label came from: hand-built, mapped from ITBench, generated by a rule, or reviewed by a human.
ITBench-LiteIBM's public dataset of real fault scenarios. 35 of the incidents come from it.
Simulated agentA stand-in agent with no AI, used so tests and experiments run offline and for free.
DuckDBA small file-based database where every run is saved.
GatewayThe backend web server the console talks to.
SSE (live stream)How the server pushes each loop step to the browser the moment it happens.
Mock mode / live modeThe console running on built-in fake data, or against the real backend.
Schema / PydanticThe defined shape of each piece of data. The frontend's types are generated from it.
