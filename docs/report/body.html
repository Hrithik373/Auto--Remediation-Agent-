1Introduction

1.1Problem

Site-reliability engineering is moving from runbooks toward agents: an LLM reads an incident's telemetry, forms a diagnosis, and proposes a remediation such as rolling back a deployment, scaling a service or disabling a feature flag. The diagnosis step is now often good. The hard part is the step after it. A proposal that is fluent and plausible can still be operationally wrong in ways that make the incident worse, for example:

  • cordoning a healthy node,
  • scaling a shared dependency to zero,
  • restarting the database every service depends on, or
  • switching on a fault-injection flag.

Letting such an agent act directly on a production control plane is unsafe. Making it ask a human every time throws away the autonomy that motivated it.

1.2Approach

This project treats the LLM strictly as an untrusted planner. Proposal generation is separated from execution, and every proposed action must pass a pre-execution verifier before it can reach the environment. The verifier is layered:

  • a deterministic envelope that never consults a model: allow-listed action types, typed and bounded parameters, a blast-radius cap, and forbidden namespaces;
  • an independent LLM judge (v1);
  • a learned verifier (v2) that outputs a calibrated probability that the action is destructive.

A single risk threshold τ combines the layers: an action executes only if the envelope passes it and its risk is below τ. Sweeping τ produces a measured safety–autonomy trade-off (a Pareto curve) rather than a single operating point.

1.3Contributions

  1. A layered pre-execution verification architecture for AIOps remediation. It is independent of the agent, records every layer's decision on every verdict, and enforces the safety rules in code: nothing executes without an allow verdict and an explicit configuration opt-in.
  2. An offline, cluster-free evaluation environment of {{n_incidents}} incidents. Thirty-five of them are converted from IBM's ITBench-Lite SRE scenarios by a converter that records the provenance of every label and keeps ground truth out of agent-visible telemetry.
  3. A learned, calibrated risk model evaluated with incident-level cross-fitting, and compared against a type-only baseline so that its gains are not overstated.
  4. A reproducible evaluation harness. {{n_runs}} seeded runs are stored as rows in DuckDB, and one command regenerates every number and figure in this report.
  5. A live triage console that streams the loop step by step and shows the layered verdict. A headless-browser rehearsal of the demonstration checks it end to end.

1.4Scope

The project studies operational correctness: whether a well-intentioned but fallible agent's action would harm the system. It does not study adversarial safety such as prompt injection or jailbreaks. All results in this report come from the offline environment with a simulated planner. The LLM-backed baselines are implemented and tested, but their evaluation is left as a cost decision (§10.3).

2Background

2.1LLM agents for incident remediation

An AIOps remediation agent sees an incident through its observability signals:

  • logs, metrics and traces;
  • the service topology;
  • firing alerts.

It must output an action against the control plane. Benchmarks such as Microsoft's AIOpsLab and IBM's ITBench [1] run these tasks against faults injected into microservice systems. Most of the agent's mistakes are not malicious. They are wrong actions taken confidently: the agent targets the component that shows symptoms instead of the cause, or picks an action whose blast radius is out of proportion to the fault.

2.2Guarding agent actions

Three families of controls are common:

  • allow-lists and policy engines: deterministic, auditable and cheap, but blind to whether a structurally valid action is right for this incident;
  • LLM-as-judge review: semantically aware, but costly, non-deterministic, and itself fallible;
  • learned risk models: cheap at inference and calibratable, but only as good as their labels.

This project composes all three and measures what each layer adds. The headline question is which layer caught which destructive proposal, reported as the prevention partition (§9.2).

2.3The safety–autonomy trade-off

Any verifier trades two errors against each other:

  • missing a destructive action (unsafe execution);
  • blocking a correct one (false block, lost autonomy).

The project reports both sides at every threshold: bad-action-prevented against false-block, and resolution against τ. It also separates the verifier's own errors from the orchestration policy's response to a block (§9.3). In the results these turn out to matter as much as each other.

3Requirements and Design Principles

Five rules govern the whole design. They are enforced in code and covered by tests, not just written down as conventions.

Table 2. Design principles and where they are enforced.
PrincipleEnforcement
The LLM is an untrusted planner. No action reaches real execution without passing the verifier policy. Executor.run(dry_run=False) raises ExecutionRefused unless it is given an allow verdict; rollback only plans an inverse action, which must itself be verified.
Real execution is opt-in. auto_execute is false everywhere by default. Default config ships auto_execute: false (tested). The gateway returns HTTP 403 for dry_run=false unless the loaded config opts in.
Typed contracts. Every cross-module payload is a Pydantic model. src/sentinel/schemas; the console's TypeScript types are generated from these models, never hand-written.
Offline first. The system runs end to end with no cluster and no API key. OfflineEnvAdapter, the simulated planner, and lazy imports of the Anthropic SDK and cluster clients. A fresh clone passes the full test suite with no network.
Independence. The agent and the verifier share no state or prompts. Separate prompts, separate LLM client handles and separate usage ledgers. The judge sees the proposal only as data. Ground-truth labels are attached after the verdict.

Two further requirements shape the evaluation:

  • reproducibility: all randomness is seeded from config, every run records a config_hash, and make eval regenerates every figure from scratch;
  • persistence: a result does not exist unless it is a run record in DuckDB.

6Component Design

6.1Environment adapter

EnvAdapter is the only interface that touches a benchmark. It has six methods:

  • list_incidents and get_incident;
  • apply_action(action, dry_run);
  • evaluate, the oracle's check of whether the incident is resolved;
  • ground_truth_action_safe, a label source for evaluation;
  • reset.

OfflineEnvAdapter implements it over JSON fixtures. Applying an action outside a dry run sets the incident's resolved flag only if the action matches a fixture entry with resolves: true. Matching is exact first. A looser match then requires every shared parameter to agree, ignoring only volatile identifiers (pod_name, revision, cache_key). This rule closed a defect: under the earlier (type, target) match, disabling an unrelated flag on flagd-config, or scaling a service to zero replicas, inherited the correct action's resolves: true (§11.2).

The AIOpsLab and ITBench cluster adapters implement the same interface as stubs and import their client libraries lazily. The rest of the system never knows which adapter is in use.

6.2Context builder and telemetry tools

build_context renders an incident within its token budget, in this order:

  1. alerts and topology, kept whole;
  2. metrics, 20% of the remaining budget, most-changing series first and downsampled;
  3. traces, 15%, error spans first;
  4. logs, 65%, error-like lines first and returned in time order.

The output is then redacted: e-mail addresses, IP addresses and credential-like values are masked. Two rules prevent ground truth leaking to the agent:

  • fault_family is never rendered.
  • The incident identifier is not rendered either, because the hand-built identifiers name their fault (e.g. pod-crashloop). A regression test caught this leak.

A signals set selects which sources are visible, which supports a telemetry ablation. The agent's four tools (get_logs, get_metrics, get_traces, get_topology) dispatch through one function. A tool whose signal is ablated is genuinely unavailable, not merely left unmentioned.

6.3Diagnosis agents

ReAct agent. The ReAct loop is written in the repository, with no agent framework. Each model turn is either a tool call (Action plus a JSON Action Input) or a Final Answer containing a ProposedAction. Tool results come back as Observation turns. Malformed turns are answered with an observation that explains the problem; they are never silently repaired. If the agent exhausts its tool budget without a valid proposal, it raises AgentExhausted and the orchestrator escalates. Verifier feedback continues the same conversation. The prompt lists the allow-listed action vocabulary but not the verifier's rules.

Simulated planner. The LLM-free SimulatedDiagnosisAgent is a controlled stimulus for evaluating the verifier, not a diagnosis method. Seeded by (seed, incident), it draws each proposal from the incident's candidate actions according to a label mix:

  • default: 45% correct, 25% ineffective, 20% destructive, 10% out-of-envelope;
  • after verifier feedback, the weight on correct actions grows by a factor of 1.5.

The planner reads labels in order to choose, but every proposal it emits carries the same label-independent rationale template, so no verifier can recover the label from its wording (this is tested).

6.4The verification layers

6.4.1Envelope (hard gate)

The envelope is driven entirely by config/action_envelope.yaml (Tab. 5). It blocks:

  • any action type that is not allow-listed;
  • parameters that are missing, mistyped, out of range, outside an enumeration, or not declared at all;
  • actions on a forbidden namespace (kube-system);
  • actions whose blast radius exceeds the policy cap (medium).

An allowed action is given an approximate risk from its blast radius (low 0.10, medium 0.35), so that the envelope-only baseline still responds to τ.

Some protections are structural. The replicas floor of 1 makes every scale-to-zero proposal impossible. The kind enumeration on remove_fault_injection means that action can delete a chaos experiment or a NetworkPolicy, but never a Deployment, PVC or Namespace.

{{envelope_table}}

6.4.2LLM judge (v1)

The judge receives a compacted rendering of the incident plus the proposal as JSON. It must answer with {decision, risk_score, reasons}, where:

  • the reasons are human-readable, one per entry, because they appear in the console;
  • the risk score is clamped to [0, 1].

The judge fails closed. If the model is unreachable, or its output cannot be parsed into a verdict, the result is block with risk 1.0 and the cause stated as the reason. An unreadable judge never lets an action through. The judge has its own system prompt, its own client handle and its own usage ledger, and it never sees the agent's conversation.

6.4.3Learned verifier (v2)

The learned verifier estimates P(destructive) with gradient-boosted trees: 150 trees of depth 3, with Platt calibration. Its features (Tab. 6) come only from what a verifier may legitimately observe:

  • the incident's telemetry and topology;
  • the proposal itself;
  • the envelope's static description of the action type.

It never uses the oracle, fault_family or the incident identifier. A test checks that features are identical when the identifier and the fault family are blanked out. The central signal is linkage: whether anything in the telemetry points at the action's target.

Table 6. Learned-verifier features (verifier/features.py).
GroupFeatures
Actionaction-type one-hot (10), scope one-hot, blast radius, reversibility, replicas (and presence), enabled flag, parameter count

The training protocol is described in §8.4. At run time, each incident is scored by the cross-fitted model that held it out during training; incidents never seen in training use a model fit on all of them. The verdict's reasons are the model's own top per-feature contributions, rendered as text, for example "target is not named by any firing alert".

6.4.4Combination policy and variants

CombinedPolicy implements final = envelope_pass ∧ (score < τ):

  • If the envelope blocks, the result is block, and the secondary layers are recorded as skipped (envelope already blocked).
  • Otherwise the score is the maximum risk over the active secondary layers, the most cautious reading.
  • At or above τ, the decision is revise only if some layer over τ asked for revision and none asked to block; otherwise it is block.

The five variants in Tab. 7 are built from the same pieces.

6.5Executor

The executor is the only caller of apply_action. A dry run needs no verdict, because it changes nothing. A real apply is refused unless both conditions hold:

  • the executor was constructed with auto_execute=true;
  • the caller passes the policy's verdict, and that verdict is allow.

Environment failures are recorded as results rather than raised, so a run always produces a record. Rollback deliberately only plans an inverse action, and only when the inverse is fully determined by the original action (e.g. flipping a feature flag back). The inverse is an ordinary proposal that must pass the verifier, so rollback cannot become a way around the safety rules.

6.6Orchestrator loop

Every run starts with env.reset, so no state leaks between runs (a test checks this). A dry-run session ends as soon as a vetted plan exists. A real run ends when the oracle reports the incident resolved. unsafe_action_reached_exec, the key safety field, is set only if an action labeled destructive was executed outside a dry run. on_block controls what a block means:

  • escalate (the blueprint default): page a human and end the run;
  • retry: feed the block reasons back to the agent.

§9.3 shows that this policy choice matters as much as the verifier itself. An on_step callback lets the gateway stream each step as it is produced.

6.7Run store

DuckDB holds a runs table and a steps table:

  • one runs row per run: experiment, cell, variant, τ, seed, agent kind, config hash, outcome fields and the full RunRecord JSON, for lossless round-trips;
  • one steps row per step: action, decision, each layer's decision, the label, executed and resolved flags, tokens and latency, for SQL analysis.

A human_decisions table records console approvals and rejections for audit; it never triggers execution. Grid writes are batched in one transaction and are idempotent per run_id, so re-running an experiment replaces its rows instead of duplicating them.

6.8Gateway and console API

The FastAPI gateway serves four things:

  • /chat, an LLM proxy with a token and cost ledger and a disk cache;
  • /usage;
  • /metrics;
  • the console API under /api.

POST /api/runs starts the real orchestrator in a background thread, with a fresh environment instance per run so that concurrent runs cannot interfere. GET /api/runs/{id}/stream is a Server-Sent Events stream. It emits one step event per StepRecord as the loop produces it, then a final event with the RunRecord, and a reconnecting client replays the whole event log. The /api/experiments/* endpoints rebuild their tables from the same DuckDB rows and the same report code as this document, so the console and the report cannot disagree.

6.9Observability and deployment

Prometheus counters and histograms instrument the live loop:

  • verdicts by decision and variant, and per-layer verdicts;
  • executions by mode;
  • destructive proposals that were blocked versus executed;
  • runs by outcome, step latency, and LLM tokens and cost.

A provisioned Grafana dashboard charts them using the console's decision colors. These are operational telemetry only; evaluation results live in DuckDB. Fig. 4 shows the containerised deployment.

6.10Triage console

The console is a React and TypeScript application. Server state lives in TanStack Query and UI state in Zustand; the live loop is an EventSource, never polling. It has four screens:

  • Queue: the incident list.
  • Triage: telemetry, topology graph, run controls (verifier, τ, dry run) and the streaming loop timeline.
  • Results: the Pareto chart with a draggable τ marker synchronised with the run controls, the prevention partition, metrics and ablations.
  • Observability: embedded Grafana.

The VerdictCard always shows all three layers and greys out inactive ones, because the layered view is the project's contribution. Two conventions hold throughout:

  • Color means decision: allow, block, revise and escalate each have one reserved hue.
  • Chart series use a separate categorical palette, validated for color-vision deficiency against the console's actual surface.

In mock mode, the console runs fully against an in-browser mock server with a measured snapshot of the evaluation, so it can be demonstrated with no backend.

7Dataset and Ground Truth

7.1Incidents

The offline environment holds {{n_incidents}} incidents across {{n_families}} fault families (Tab. 8). Each is a JSON fixture with five parts:

  • telemetry: logs, metrics, traces, topology and alerts;
  • an oracle: candidate actions labeled under the taxonomy of §7.3;
  • the resolving action;
  • a provenance tag on every label;
  • for converted incidents, an eval-only block holding ITBench's root cause and causal chain.

Six incidents are hand-built (crash loop, bad rollout, memory leak, connection-pool exhaustion, disk pressure, misconfiguration). The other 35 are converted from ITBench-Lite [1], IBM Research's public SRE snapshots (Apache-2.0), and are cited in the repository's third-party notices.

7.2ITBench conversion pipeline

Three design decisions in the converter matter for validity.

The action envelope was extended. Most ITBench remedies are configuration-level: disabling a feature flag, removing a chaos experiment, raising a namespace quota. With the original seven action types, only 7 of 35 scenarios had any allow-listed fix. Three narrowly typed actions were added (toggle_feature_flag, remove_fault_injection with its kind enumeration, and increase_namespace_quota). Fixes to an environment variable, image, command or node selector map to rollback_deployment. With these, 34 of 35 scenarios are resolvable within the envelope. The remaining one, Scenario-38, lists only investigation steps and serves as a "should escalate" case.

Ground truth is kept out of telemetry. Root-cause flags and the causal descriptions in ITBench's ground truth describe the answer, so they are stored only in the eval-only block.

Telemetry is sampled around the first alert. The window runs 30 minutes before the earliest firing alert to 10 minutes after it. Faults begin well before alerts fire, and in some scenarios the capture ends before the alert does; in that case the window anchors on the end of the capture and the fixture records which anchor was used.

7.3Label taxonomy and provenance

Each candidate action carries one of four labels:

  • correct: in the appropriate remediation family for the fault, and resolves it;
  • ineffective: valid and safe, but does not resolve the incident;
  • destructive: high blast radius or harmful to healthy components; the class the verifier must catch;
  • out_of_envelope: action type not on the allow-list.

Because the ground truth itself will be questioned, every label also records where it came from (Tab. 9).

7.4Hard cases: why the dataset needed them

A negative result, corrected and kept in view

In the first version of the dataset, the label was fully determined by the action type: every cordon_node was destructive, every replicas: 0 was destructive, and every restart_pod was safe. A type-only classifier scored AUC 1.0, so the learned verifier's near-perfect AUC said nothing about whether it understood the incident.

Four documented rules (config/labeling_rules.yaml) add within-type contrasts: the same action type, safe on one target and harmful on another.

All metrics are defined once, in eval/metrics.py; the report, the notebook and the console call the same functions. Rates computed over labeled steps exclude unlabeled steps, and those are counted separately. A metric whose denominator is empty is reported as undefined, never as zero.

8.2Experimental grid

The evaluation runs {{n_cells}} configuration cells × {{n_incidents}} incidents × {{n_seeds}} seeds = {{n_runs}} runs, against the offline environment with real (simulated-environment) execution enabled. The cells are:

  • baselines at τ = 0.5: ungated, envelope only, envelope + learned;
  • τ sweep over {{tau_grid}} for envelope-only and envelope + learned;
  • block handling: escalate versus retry;
  • topology features: the learned model retrained without topology features;
  • agent quality: strong, default and weak planner label mixes, each crossed with {none, envelope, learned}.

8.3Uncertainty

95% confidence intervals use a bootstrap with {{bootstrap}} resamples. It resamples incidents, taking all seeds of an incident together, because seeds of one incident are not independent evidence. The bootstrap is seeded, so the intervals are reproducible too.

8.4Learned-verifier protocol

The target is label = destructive. Out-of-envelope actions are excluded because the deterministic layer owns that class and the learned layer never sees such actions at run time. The model is reported against a type-only baseline: logistic regression on action-type indicators plus replicas = 0 and enabled = true, under the same cross-fitting. It is also reported on the within-type subset: action types that occur with both labels, where the type alone cannot decide.

The envelope alone prevents {{prev_env}} of destructive proposals, with no false blocks. These are the scale-to-zero proposals, which its replicas floor makes impossible. 9.2Which layer caught what

This is the project's central figure. It shows that each layer earns its place. The envelope catches the structurally impossible actions cheaply and deterministically. A residue of structurally valid but destructive actions remains — cordoning healthy nodes, restarting shared stateful dependencies, enabling fault flags — and only a semantic layer catches it.

9.3Escalation versus retry

{{block_table}}

Under the blueprint's escalate-on-block policy, every block ends the run and pages a human. The ungated agent "resolves" more incidents only because it keeps acting, including destructively, and then continues. When block reasons are fed back to the agent instead, the learned variant resolves {{res_learned_retry}} of incidents with {{unsafe_learned_retry}} unsafe execution. Its net-safe resolution is {{netsafe_learned_retry}}, against {{netsafe_none}} for the ungated agent.

The safety–autonomy trade-off therefore has two separate dials:

  • the verifier threshold τ;
  • what the loop does after a block.

9.4The risk–autonomy Pareto

For the learned verifier, the frontier is short: prevention stays between {{pareto_prev_range}} while false blocks range over {{pareto_fb_range}} across the sweep. That shortness is itself a finding. On this dataset the calibrated model separates the classes well enough that τ matters little between 0.2 and 0.9. Whether the frontier stays this favourable with real LLM proposals and human-reviewed labels is the main open question (§10).

10.2Interpretation

The results support the architectural claim more strongly than any single number. A deterministic gate is necessary and cheap, but it is not sufficient: it leaves a residue of structurally valid, destructive actions. A semantic layer can close most of that residue at a small false-block cost. Measuring the composition required infrastructure that is as much a contribution as the model:

  • layer-attributed verdicts;
  • labels with provenance;
  • incident-level cross-fitting;
  • a run store from which every figure is regenerated.

The most consequential design choice turned out not to be the verifier at all, but the orchestrator's response to a block.

11.3Verification of the live demonstration

make e2e starts the real gateway and the console in live mode, then drives a headless Chromium browser through four checks:

  1. the queue lists every incident;
  2. the happy path (bad-rollout-latency, learned verifier) streams and resolves, with no unsafe execution;
  3. on itbench-sre-scenario-12, the envelope passes a destructive cordon_node and the learned layer blocks it;
  4. the same incident, run ungated, executes the action.

It then checks that the results screen renders from the run store, and it fails on any browser console error. It currently passes.

12Limitations and Future Work

  1. LLM evaluation. Run the ReAct agent and the LLM judge (make eval WITH_LLM=1), including the telemetry-signal and model-size sweeps. This replaces the simulated planner with real proposals and the rule-based secondary layer with a semantic judge.
  2. Human-reviewed gold labels. Review the rule-derived labels with the review CLI. The first targets are the low-confidence mappings flagged by the converter. Then report metrics on the human-reviewed subset.
  3. Cluster integration. Implement the AIOpsLab and ITBench adapters against the existing interface, so that actions have real, partial and delayed effects.
  4. Richer contrastive data. More within-type hard cases, and node-level faults where cordoning is the correct action, so that no action type keeps a single label.
  5. Learning from escalations. Human approve/reject decisions are already recorded; use them as labels for continual recalibration of the learned verifier.

13Conclusion

sentinel-remediate shows that an LLM remediation agent can be given real autonomy safely if it is treated as an untrusted planner, and if every proposal passes a layered, independently auditable verifier before it reaches the control plane. The deterministic envelope gives cheap, absolute guarantees about structure. A calibrated semantic layer closes most of the residue of structurally valid but destructive actions. With block reasons fed back to the agent, the system resolves most incidents while almost never executing a destructive action. The results come with the infrastructure needed to question them: label provenance, honest baselines, incident-level cross-fitting, stated non-runs, and a single command that regenerates every number and figure.
