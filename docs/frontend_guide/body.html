1What the Console Is

1.1Purpose

The backend makes decisions: the agent proposes a remediation, the verifier rules on it, and the executor acts only on an allow. The console makes those decisions visible, and it was designed around the live demonstration. In about three minutes, a viewer should see:

  1. an incident's evidence (logs, metrics, traces, alerts, topology), much as an on-call engineer would;
  2. the agent's proposal and the verifier's verdict, layer by layer;
  3. a destructive action that the deterministic envelope passes and the learned layer blocks. This is the project's thesis on one screen;
  4. the aggregate evidence: a Pareto curve, the prevention partition, and baselines.

The dependency rule

Data flows one way: routes → features → api hooks → api client → network. Components never call fetch directly, and nothing outside api/ knows URLs. That is why mock mode can replace the whole backend without touching a single component.

5Boot Sequence, Mock Mode and Live Mode

5.1What happens when the page loads

  1. index.html loads src/main.tsx.
  2. main.tsx runs enableMocking(). If VITE_USE_MOCKS is anything other than "false", it starts the MSW worker from mock/browser.ts and waits for it before rendering. This avoids a race in which the first fetch escapes to a backend that isn't there.
  3. It creates one QueryClient (10 s stale time, one retry, no re-fetch on focus) and renders <App/> inside QueryClientProvider.
  4. App.tsx draws the header (logo, navigation, mode indicator) and a <Routes> switch that mounts one screen.

5.2Mock mode

MSW installs a service worker (public/mockServiceWorker.js) that intercepts the page's network requests and answers /api/* from mock/handlers.ts. To the rest of the app the responses look exactly like real ones, because handlers return the same JSON shapes and use the same generated types. Unmatched requests (fonts, images) pass through untouched.

  • Incidents come from mock/fixtures.ts: six incidents mirroring the hand-built backend fixtures, with full telemetry for the two used in the demo.
  • Runs are simulated. POST /api/runs picks a canned RunRecord. The stream handler then replays its steps as genuine SSE events, about 0.9 s apart, so the timeline really streams. This is a demo device, not a real orchestrator.
  • Results are measured. mock/experiments.json is a snapshot of the real make eval output, written by make mock-results. Mock mode therefore shows real numbers, and the Results header says which experiment they came from.

5.3Live mode

With VITE_USE_MOCKS=false (set by .env.live, used by npm run dev:live), MSW never starts and requests go to /api on the same origin:

  • In development, Vite's proxy forwards them to VITE_API_TARGET (default http://localhost:8080).
  • In Docker, nginx forwards them to the gateway with buffering off, so the SSE stream is not held back.

The same-origin /api path means the browser never needs CORS. The header's mode indicator reads the same variable, so you can always tell which mode you are looking at.

6The Screens, One by One

6.1Queue

QueueRoute calls useIncidents() (GET /api/incidents) and hands the list to IncidentTable. Each row shows:

  • the incident ID, in monospace because it is machine output;
  • the source tag (offline or itbench);
  • the fault-family tag;
  • the alert count;
  • a status dot.

The status comes from the latest console run of that incident: queued if never run, then resolved, blocked or escalated. Its color is a decision color (§11.1). Clicking a row calls navigate("/incidents/<id>").

6.2Triage

TriageRoute reads :incidentId from the URL, loads the incident with useIncident(id), and holds one piece of local state: the runId of the run it is showing. It passes that ID to useRunStream(runId). The layout is a three-column grid: evidence and the loop trace across two columns, run controls in a narrow right column.

6.2.1TelemetryPanel

Four tabs, held in local state:

  • Logs: monospace, with lines containing FATAL or ERROR in the block color.
  • Metrics: one small bar per data point, scaled to the series maximum. Bars, not a chart library, because this is a sparkline-style glance, not an analysis tool.
  • Traces and Alerts: pretty-printed JSON in CodeBlock.

The generated types mark telemetry fields as optional (?). The backend defaults them to empty lists or maps but JSON Schema does not say so, so the panel normalises them once with ?? [] and ?? {}.

6.2.2TopologyGraph

The topology graph is built with React Flow:

  • Each service in telemetry.topology.services becomes a node, laid out left to right in a zig-zag.
  • Each [source, target] pair becomes an edge.
  • A service is drawn red if some alert's target starts with its name, so payments-api matches the pod payments-api-7d9f-xk2z.
  • Edges touching a red node are animated.
  • Nodes can't be dragged or connected; the graph is for reading, not editing.
  • The layout is computed in useMemo, so it is only redone when the telemetry changes.

6.2.3RunControls

Run Controls holds the experiment's three knobs, all stored in Zustand:

  • Verifier: Ungated (none), Envelope only, Learned (default; works offline), LLM-judge and Combined. The last two need an API key on the gateway; without one the judge fails closed and blocks everything.
  • Risk threshold τ: 0–1 in steps of 0.05.
  • Dry-run: when ticked, the run ends at the first vetted plan and nothing is applied.

Start run calls useStartRun(), a TanStack mutation. On success it hands the new run_id up to TriageRoute. The button is disabled while a run is connecting or streaming.

6.2.4DiagnosisCard

The Diagnosis card appears once a run has produced a step. It shows the latest proposal's rationale and predicted_effect, which is the agent's own account of what is wrong and what its action will do. Because the agent is an untrusted planner, the card only states its claim; the VerdictCard is where that claim is judged.

6.3Results

Four hooks fetch the four tables in parallel. The header line says where the numbers came from (live: rebuilt from the gateway's DuckDB run store, or the mock snapshot's experiment). If the store has no evaluation yet, the screen asks you to run make eval instead of showing empty charts.

  • ParetoChart: bad-action-prevented (y) against false-block (x) across τ, one line per verifier variant.
    • Colors are keyed by variant (envelope blue, learned orange, judge aqua), never by position, so a missing series cannot repaint the others.
    • The τ slider moves a marker to the nearest swept point on each line. It is the same τ as in Run Controls.
  • PreventionPartition: for each baseline, a stacked bar splitting destructive proposals into missed (reached the executor), caught by envelope and caught by judge/learned only. "Missed" is magenta and sits first, against the baseline, where its length is easiest to compare (§11.2).
  • MetricsGrid: resolution, bad-prevented, false-block, MTTM and cost per baseline. It is a table, not a chart, because readers compare exact values.
  • AblationTable: rows grouped by ablation. Rates are shown as percentages; step counts as plain numbers.

6.4Observability

This screen embeds Grafana in an <iframe> when VITE_GRAFANA_URL is set. With make demo, it shows the provisioned "sentinel — live loop" dashboard: verdicts by decision, destructive actions blocked versus executed, runs by outcome, step latency and LLM spend. The rule is embed Grafana, don't rebuild it.

7The Live Run, Step by Step

This is the most important flow in the console. Fig. 10 traces one click of Start run from the button to the run summary.

7.1Why EventSource and not polling

A run produces steps one at a time. Polling would either lag behind (a slow interval) or hammer the server (a fast one), and would replay steps it had already seen. Server-Sent Events invert this: the backend pushes each StepRecord the moment the orchestrator emits it. The browser's EventSource handles reconnection, and the gateway replays the full event log to a reconnecting client.

The live run is deliberately not a TanStack Query. It is a stream with its own lifecycle, and it touches the Query cache only once, to invalidate ["runs"] when it finishes.

7.2The stream's states

7.3Reading a timeline step

Each step row shows the step index, action type and target, and an outcome pill. The pill is derived from the step itself by outcomePillForStep (Tab. 7). Clicking the row expands it to show the ActionCard and the VerdictCard. The first step, and any step that was not allowed, start expanded, because those are the steps worth reading.

8The VerdictCard

The VerdictCard is the project's contribution made visible. A collapsed "BLOCK" would hide the point. The card shows the whole decision pipeline, so a viewer can see which layer passed an action and which layer caught it.

Table 8. How the VerdictCard renders a Verdict (src/features/triage/VerdictCard.tsx).
PartRule
Header badgeThe final decision (ALLOW, BLOCK, REVISE) in its decision color. The card's ring uses the same color.
One row per layerAlways all three, Envelope · LLM-judge · Learned, from verdict.layers. Never only the final decision.
Inactive layerDecision skipped → the row at 40% opacity with "not active for this run". It is shown, never hidden, so the viewer sees which layers were in play.
Active layer✔ Allow / ✘ Block / ⟲ Revise in its decision color, the layer's risk, and (for secondary layers) the τ it was compared with.

How to explain Fig. 12 in one sentence

"The deterministic gate can only check structure. cordon_node is a legal action with valid parameters, so the envelope passes it. The learned layer sees that nothing in the telemetry points at that node, scores it as destructive, and blocks it before it reaches the executor. Run the same incident ungated and the cordon executes."

src/api/client.ts is a thin wrapper. apiGet and apiPost prefix /api, send and parse JSON, and turn a non-2xx response into an ApiError carrying the HTTP status. sseUrl builds stream URLs. Every hook is built on these three functions.

The backend also refuses some requests, and the console surfaces the reason:

  • 403: a real (non-dry-run) start when the gateway's config does not allow execution;
  • 409: the learned variant requested but no trained model exists (make train);
  • 404: an unknown incident or run.

10Types Shared with the Backend

types.ts defines IncidentContext, Telemetry, ProposedAction, Verdict, LayerVerdict, StepRecord and RunRecord exactly as the backend does. Never edit it by hand. When the UI needs a new field:

  1. add it to the Pydantic model;
  2. run make types;
  3. let the TypeScript compiler show every place that must handle it.

Fields with defaults in Pydantic become optional (?) in TypeScript, which is why components write verdict.layers ?? []. A few response shapes are not Pydantic models, because they are tables computed by the evaluation report: IncidentSummary, ParetoPoint, MetricsRow, PreventionRow and AblationRow. Those are typed by hand in mock/fixtures.ts and must be kept in line with gateway/api.py.

11Design Rules

11.1Color means decision, everywhere

Four hues are reserved for the four outcomes. They appear on pills, verdict bands, timeline dots, status dots and Grafana panels. The tokens are defined in tailwind.config.ts and mapped to class names in lib/decisionColors.ts. Components import those class names and never hard-code an allow or block color.

Table 10. Decision tokens (dark console theme).
DecisionTokenHexUsed for
allowdecision-allow#34D399allowed or resolved; "no" on unsafe execution
blockdecision-block#F87171blocked, unresolved, FATAL/ERROR log lines, alerting topology nodes
revisedecision-revise#FBBF24revise; queued status
escalatedecision-escalate#A78BFAescalated to a human
accentaccent#22D3EEinteractive elements only (buttons, active tab, slider): never a decision

11.2Charts have their own palette

Chart series are identities (which verifier), not decisions, so they use a separate categorical palette. Each palette was checked with the dataviz skill's color validator against the console's actual dark card surface: lightness band, chroma, separation under color-vision deficiency, normal-vision separation and contrast.

  • ParetoChart: envelope #3987e5, learned #d95926, judge #199e70, keyed by variant.
  • PreventionPartition, stacked in this order: missed #d55181 (magenta), caught by envelope #3987e5, caught by secondary #d95926.
    • An earlier version drew "missed" in green, which read as "good".
    • Red, amber, emerald and violet are reserved for decisions, so they were not options.
    • Magenta passes the validator only when it is not next to orange. Hence its position first, against the baseline.

11.3Typography, density and motion

  • Monospace for anything a machine emitted: IDs, action types, parameters, log lines, risk scores, durations. Everything else uses the sans-serif UI font.
  • Dense and dark, like an on-call tool: compact tables, small uppercase card titles, and space reserved for the two things people read closely (the VerdictCard and the RunSummary).
  • Minimal motion:
    • new timeline steps fade in (0.2 s);
    • the in-progress dot pulses;
    • chart animation is off, so a screenshot never catches a half-drawn bar;
    • everything is disabled under prefers-reduced-motion.
  • Accessibility: a visible focus ring (accent), text labels beside every colored dot or pill, and hover titles on verifier buttons.
  • No browser storage. UI state lives in memory (Zustand); nothing goes to localStorage.

12Recipes: Changing the Console

12.1Show a new backend field

  1. Add the field to the Pydantic model in src/sentinel/schemas/.
  2. Run make types. types.ts now has it.
  3. Render it in the component, using lib/format.ts for numbers and monospace if it is machine output.
  4. If mock mode should show it, add it to mock/fixtures.ts.
  5. Run npm run typecheck, npm run lint and make e2e.

12.2Add an endpoint and a hook

  1. Add the route in src/sentinel/gateway/api.py, reusing the schemas.
  2. Add a hook in src/api/ with useQuery (reads) or useMutation (writes), and a distinct query key.
  3. Add a matching MSW handler in mock/handlers.ts, so mock mode keeps working with the backend down. This is required.

12.3Add a screen

  1. Create src/routes/XRoute.tsx: fetch with hooks, compose features.
  2. Register it in App.tsx: a <Route>, plus a NAV_ITEMS entry if it belongs in the header.
  3. Put real components under src/features/x/, built from features/shared/ (Card, Tag, StatusDot, CodeBlock).

12.4Change a color

  • Decision colors: change the token in tailwind.config.ts. Every pill, band and dot follows.
  • Chart colors: re-run the palette validator against the console surface before changing any hex, and keep colors keyed by entity.

12.5Refresh the numbers shown in mock mode

Run make eval, then make mock-results. The second command rewrites mock/experiments.json from the new results.

14Questions to Expect in a Viva

Table 13. Likely questions and short answers.
QuestionAnswer
Why show every layer instead of just the final decision?The contribution is the layering. Showing the envelope passing an action and the learned layer blocking it is the evidence that each layer earns its place.
How does the live trace work?Server-Sent Events. The gateway runs the orchestrator in a background thread and pushes each StepRecord as it is produced; the browser's EventSource appends it to the timeline. No polling.
Can the demo run without the backend?Yes. In mock mode MSW intercepts /api in the browser and replays canned runs over real SSE. The results shown are a measured snapshot of the evaluation.
How do you keep frontend and backend in sync?The TypeScript types are generated from the Pydantic models (make types). A schema change fails the TypeScript build instead of failing silently at runtime.
Why TanStack Query and Zustand?They hold different things. Query caches server data with refetch and retry; Zustand holds a few UI values shared across screens, such as τ in both Run Controls and the Pareto marker.
Why is "missed" magenta in the partition chart?Green read as "good"; red, amber, emerald and violet are reserved for decisions. Magenta passed the color-vision validator only when placed away from orange, so it sits first, against the baseline.
Can the console execute something unsafe?No. It only requests runs. The gateway refuses real execution unless its config allows it, the executor requires an allow verdict, and human approve/reject decisions are recorded for audit but never execute anything.
How do you know the demo works?make e2e drives a headless browser through the demo against the real gateway: happy path, blocked cordon, ungated execution, results. It fails on any browser console error.
